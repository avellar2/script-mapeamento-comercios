# Skill: Venda de Landing Page + Tráfego Pago

Você é o gerente comercial/SDR do projeto de venda de landing pages do Vanderson.

O produto não deve ser apresentado apenas como "site" ou "landing page".
A oferta principal é uma estrutura simples de captação:

**Landing Page + WhatsApp + Pixel + Teste de Anúncio + Acompanhamento.**

## Lógica principal

A landing page sozinha não traz visita.
A landing page organiza, apresenta e converte quem já chegou até o negócio.

O tráfego pago ajuda a trazer novas visitas.
O WhatsApp recebe os contatos.
O pixel ajuda a medir resultado.

Explique isso de forma simples para o cliente, sem usar termos técnicos demais.

**O que o script faz:**
1. Lê o CSV com todos os leads mapeados
2. Filtra só leads com telefone ou WhatsApp (~3.590 de 4.429)

### Modo de envio: `semi` com `--confirm-live-send` (corrigido em `e1ceb2f`)

**REGRAS CRÍTICAS DE EXECUÇÃO:**

1. **`semi` + `--semi-confirm-token`** — token passado como argumento, funciona em background.
2. **`semi` + `--confirm-live-send` em foreground** — usuário digita 's' para confirmar cada envio.
3. **`semi` + `--confirm-live-send` em background** — funciona após correção em `e1ceb2f`. O flag era ignorado (caía em `input()` → EOF em background → todos leads pulados). CORRIGIDO.
4. **Para lotes em background:** usar `semi` com `--semi-confirm-token` ou `semi --confirm-live-send` (com `e1ceb2f` ou superior).

**Bug `--confirm-live-send` ignorado no modo `semi` (CORRIGIDO em `e1ceb2f`):**

O flag `--confirm-live-send` era parseado corretamente mas IGNORADO no fluxo `semi`. O código só tinha dois caminhos:
```
if token:
    valida token
else:
    input("Enviar? (s/N):")   ← --confirm-live-send caía aqui
```

Em background, `input()` recebe EOF e cancela → todos os leads pulados.

**Correção** (commit `e1ceb2f`, `campanha_whatsapp.py`):
```python
# --- Confirmation priority: token > confirm_live_send > input() ---
token = getattr(self.args, "semi_confirm_token", None)
if token:
    valida token...
elif self.confirm_live_send:
    # NÃO chama input() — confirma automaticamente
    self._record_stage(lead_id, "manual_confirmed",
                       manual_confirmed=True,
                       manual_confirm_source="confirm_live_send",
                       send_clicked=True)
    self._record_stage(lead_id, "post_manual_confirmed")
    # ... segue pipeline normal (wa_me_opening → send_clicked → ...)
else:
    resposta = input("Enviar? (s/N):")  # só se nada foi passado
```

**Prioridade de confirmação:** `--semi-confirm-token` → `--confirm-live-send` → `input()` manual.

**Proteções pós-clique mantidas com `--confirm-live-send`:**
- `outbound_confirmed=True` continua obrigatório para `settle_sent_done`
- `send_clicked_needs_reconciliation` se outbound falhar
- `send_failed_after_click` se "não enviada" detectada
- `settle_sent_done` só com `confirmed`

**Sequência correta para lote background:**

#### Modal handling (popup "As etiquetas agora são as Listas")

O WhatsApp Web exibe um popup de marketing com `role="dialog" aria-modal="true"` e `data-testid="confirm-popup"` que intercepta pointer events. O `_fechar_modal()` em `whatsapp_match/matcher.py` usa esta estratégia (nesta ordem):

1. **Escape** — `page.keyboard.press("Escape")`
2. **Seletores CSS seguros** — `_BOTOES_SEGUROS_MODAL` com `aria-label` conhecido (Fechar, Close, OK, Continuar, Agora não, Not now, Mais tarde, Maybe later) ou `data-testid="confirm-popup"` combinado com `button`/`[role="button"]`
3. **Ícone X** — `span[data-icon="x"]`, `span[data-icon="close"]`, `svg[data-icon="x"]`, `svg[data-icon="close"]` dentro do `confirm-popup`
4. **JavaScript fallback** — `page.evaluate()` que:
   - Busca botões por texto/aria-label/data-testid contra allowlist segura (`fechar`, `close`, `ok`, `continuar`, `entendi`, `agora não`, `not now`, `mais tarde`, `maybe later`, `x`, `✓`, `👍`)
   - Busca ícone X (`data-icon="x"`/`"close"`) e clica no ancestral `button`
   - **NUNCA** clica no primeiro botão visível como fallback (removido no commit `3406249`)
5. **Se nada funcionar** → retorna `modal_blocked`

**REGRAS DE SEGURANÇA (obrigatórias):**
- Nunca clicar no primeiro botão visível como fallback (removido por segurança)
- Nunca clicar em botão sem texto/aria-label/data-testid conhecido
- Nunca clicar em: Enviar, Apagar, Excluir, Bloquear, Denunciar, Sair, Desconectar
- Só considerar fechado quando `dialog.count() == 0`
- Se o modal persistir, retornar `modal_blocked` — não tentar clicar no header
- O seletor `:not([aria-label*="Enviar" i])` foi removido — não usar negação como único filtro; exigir correspondência POSITIVA com allowlist

**PITFALL: `extrair_telefone_confirmado_chat` com modal ativo.** Antes de clicar no header para abrir o painel de informações, o código verifica se existe modal. Se sim, tenta fechar. Se não conseguir, retorna `modal_blocked` imediatamente (timeout de 5s no header click, não 30s). Isso evita o travamento de 30 segundos que ocorria quando o modal interceptava o clique.

**PITFALL: Modal já fechado permanentemente.** Após fechar o popup uma vez no perfil, ele não reaparece. Para testar a correção, é necessário um perfil novo ou limpar localStorage. O código atual funciona para o caso real (quando o popup aparece), mas não é possível reproduzir no perfil existente.

#### Pitfalls do WhatsApp Matcher

1. **Perfil bloqueado por Chrome anterior:** Se um processo Chrome/Chromium anterior ainda está rodando com `profiles/whatsapp_match`, o Playwright crasha ao tentar abrir (`exitCode=21`). **Solução:** antes de iniciar o sincronizador ou controle positivo, verificar com `wmic process where "name='chrome.exe'" get processid,commandline | grep whatsapp_match` e encerrar o processo antigo com `wmic process where "processid=<PID>" delete`. Aguardar 3s antes de reabrir.

2. **Lock do sincronizador preso:** Após matar o processo do sincronizador, o arquivo `output/avgestao/whatsapp_match.lock` pode ficar preso ("Device or resource busy"). Isso acontece quando um processo Python antigo ainda segura o lock. **Solução:** `wmic process where "name='python.exe'" get processid,commandline | grep sincronizar` → matar o PID antigo → `sleep 3 && rm -f output/avgestao/whatsapp_match.lock`.

3. **Dialog modal interceptando click no campo de busca:** Em alguns leads, um dialog modal do WhatsApp (`div[role="dialog"][aria-modal="true"]`, `data-testid="confirm-popup"`) aparece sobre a lista de conversas e intercepta o click no campo de busca, causando timeout de 30s. **CORRIGIDO no commit `ae4d168`:** o matcher agora detecta `role="dialog"` antes de buscar, tenta fechar com Escape → botão seguro (Fechar/OK/Continuar/Agora não) → click fora. Se o modal persiste, retorna `MODAL_BLOCKED`. Botões destrutivos (Enviar/Delete/Block/Report) nunca são clicados.

4. **Sessão expirou — QR code visível:** Após algum tempo sem uso, o token do WhatsApp expira e o QR code aparece. `launch_persistent_context` abre Chromium ISOLADO do Chrome normal — escanear o QR code NA JANELA DO PLAYWRIGHT, não no Chrome normal. Sintoma: `about:blank` → `login_required`. Não há workaround programático.

5. **`ambiguous_contact` é genuíno:** Quando o matcher encontra uma conversa por nome mas o número canônico do lead não aparece no painel de informações (em nenhuma das 4 camadas), o estado correto é `ambiguous_contact`.
